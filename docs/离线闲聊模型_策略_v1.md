# 离线闲聊小模型 · 3DS 效果最佳策略 v1

> 2026-10-16 成文。综合本项目全部实测数据（钢印 v0.99 / 10-04 工作总结 /
> 10-05 语料体检 / 10-16 闲聊首轮训练），回答一个问题：
> **在 3DS 上，一个小模型怎么做到效果最佳？**
> 前提声明：本文区分【实测】与【估算】，凡是没在机器上量过的一律标估算。
> 用户授权方向：时间不限，追求最佳效果；云端链路（豆包/deepseek）已存在。

---

## 〇、一句话结论

**3DS 上小模型的"效果"，80% 由架构决定，20% 才由模型本身决定。**
本项目已经用血的事实证明了这一点：1.18M 模型自由生成教师强迫 top-1 只有
15.4%（10-04 实测），而同一套数据走 BM25 检索 + 原文抽取，评测 12/12 命中。
所以策略总纲是：

> **模型只做它独一无二的事（语言组织、泛化、语气），其余全部交给检索和模板。**
> 把模型放在"最后 20% 的长尾"上，而不是放在"每一句话"上。

## 一、3DS 的硬约束（先承认墙在哪，再谈怎么爬）

| 约束 | 数值 | 性质 |
|---|---|---|
| CPU | ARM11 MPCore，**无 NEON**；项目按 New3DS 804MHz 估算 ~25 tok/s（1.18M int8）、Old3DS 268MHz ~8 tok/s | ⚠️ **估算，非实测** |
| 缓存 | L1 D-cache **32KB** / L2 **512KB**；1.18M 主干 640KB **装不进 L2** | 实测（结构推断） |
| 内存 | New3DS FCRAM 充裕，weights 1~10MB 无压力 | 结构事实 |
| 存储 | SD 卡，体积不是瓶颈（本项目已验证 5MB 3dsx 可跑） | 实测 |
| VFP | 只有 f32，写 double = 软浮点 | 实测 |
| system tick | 268MHz，其余 svc 时间是纳秒 | 实测 |

**这三条推出所有后续结论：**
1. **无 NEON + 权重装不进缓存** → 每 token 的权重都要从 RAM 过一遍 →
   **速度由"权重字节数"决定，不由 FLOPs 决定** → int4 量化是唯一的真提速
   （本项目自己的结论："真提速只有 int4 量化"）。
2. **每条回答都是钱**：25 tok/s 下 40 token = 1.6s，用户等 3 秒以上就是失败。
   → **回答必须短**（≤40 token）或**大部分回答根本不走模型**。
3. 容量换速度是线性的：1.18M→2.88M ≈ 2.4× 慢（25→~10 tok/s 估算）。

## 三、策略总纲：五层回答架构（模型只出现在第四层）

```
用户输入
  │
  ├─ T0 精确/高相似命中（sim ≥ 阈值） ──→ 原对答案            ~0ms，覆盖高频问句
  ├─ T1 意图模板（问候/告别/感谢/自我介绍/兜底话术）─→ 模板句   ~0ms
  ├─ T2 检索抽取（chat 语料 BM25 + 选句，复用 gkb_extract）  ~几 ms
  ├─ T3 模型生成（带 1 个检索样例的上下文 prompt，≤40 token） ~1.5~4s
  └─ T4 联网时走云端（豆包/deepseek，质量无上限）
```

**为什么这是"效果最佳"：**
- T0-T2 覆盖**日常闲聊的绝大多数**（真人聊天 70%+ 是高重复问句）——零延迟、零胡编。
- T3 处理没见过的问法，用**检索到的相似问答当 1-shot 上下文**（F6 证明裸生成不行；
  128 ctx 放得下 "问→答" 一对 + 新问句，小模型对上下文样例极敏感，这是最便宜的
  "受控生成"）。
- T4 是质量天花板，但用户要的是**离线**，所以 T4 只在有网时兜底。
- **每层都有判据**（见 §五），不是"感觉快"。

**复用红利**：T2/T0 的检索核（`guide_kb.bin` 那套 BM25 + `gkb_extract`）已经为攻略
写过并验过——**闲聊语料灌进同一套 C 代码**即是 chat KB，不写新检索算法。

## 四、各杠杆详述（按 ROI 排序）

### L1 数据：质量 > 数量，且"数量"可以买时间堆出来（用户不缺时间）

现状：21.97 万对小黄鸡式 QA，浅、有错别字、人设不统一。

1. **近重复去除 + 人设统一过滤**（当前清洗只做了精确去重）：
   同一问题多个答案时保留最符合人设的；把"主人/老娘/人家"混乱自称统一成本项目人设。
2. **云端合成为主扩展源**（时间不限 + 有 deepseek key）：
   让豆包/deepseek 按人设批量生成**多轮日常对话**（话题清单驱动：天气/食物/游戏/情绪/学习/节日…），
   每轮 4-8 句，切成 (上下文→回复) 对。十万轮级别 ≈ 现有数据 2 倍以上高质量部分。
   ⚠️ 成本：要走用户充值的 API（AgentKey 余额不多，deepseek key 可用），**动手前必须报预算**。
3. ** mined 真实输入**：设备上记录"哪层回答的、胡编了没有"，回流向语料——
   这是唯一能让系统**越用越准**的机制，但涉及隐私，先做本地开关。

### L2 训练：token/参数 2.66 的数据饥饿区，epoch 是朋友不是敌人

- F7 说明**没过拟合风险之前，谈正则化是错的**：直接多 epoch（8k→12k→16k 步，
  每档 ~20-30 分钟，用留出集 loss 决定停）。
- 退火必须走完（10-04 的教训：中断 = 没退火 = 假到顶）。档位切换用全新跑法，
  resume 会把 LR 顶回峰值（脏实验）。
- 待验证的 cheap trick：**上下文 1-shot**（T3 的 prompt 形态）要在训练时就见——
  训练序列里混入 10~20% 的 `[BOS] 样例问 样例答 [SEP] 真实问 [SEP] 真实答` 形态，
  否则推理时的 prompt 分布训练时没见过（这是小模型的常见静默失效）。

### L3 词表：1.24 汉字/token 是当前最便宜的改进点之一

- chat BPE 4096 但压缩率低于攻略线的 1.8——闲聊文本短、标点/颜文字多，正常。
- d128 下 embedding 4096×128 = 52.4 万参数 = **44% 的模型都趴在查表上**。
  两个方向，用实验判：
  - **A：vocab 降到 3072/2048** → embedding 占比降到 33%/22%，层容量变相增加；
    代价是每字 token 变多、序列变长。
  - **B：维持 4096**，换更大 d_model（见 L4）。
- 颜文字/语气词（哈哈/呜呜/QAQ/~）必须占独立 token——它们是闲聊的"语气骨架"。

### L4 容量：什么时候才允许把模型变大

升容量前先满足三个条件（缺一个就不升）：
1. 同数据下 8k/12k 步的 val loss 已走平（数据吃干了）；
2. T0-T2 的覆盖率已测出来，模型的活儿确实集中在长尾；
3. 速度预算内（2.88M ≈ 10 tok/s 估算，40 token = 4s，UX 要明示"正在想"）。

档位：1.18M（d128/L4）→ 2.88M（d192/L6，RAM 无压力）→ 4~6M（d256/L6/L8，
需先解决 int4 否则速度不可用）。**不要一次跳两档**，每档留出集 + 人工样本双判据。

### L5 推理技巧：小模型专属，且几乎免费

1. **MMI 过滤（GPT2-chitchat 的核心 trick）**：生成 N=4~8 个候选，
   用同一模型算 `P(输入|候选)` 反项，取最大的。专治"安全但无聊的通用回复"。
   PC 侧先量收益；上机版是 N 次前向（贵），可降级为 temp 0.6/topk 5 的窄采样。
2. **窄采样 > 宽采样**：今日实测 temp0.8/topk20 出碎片，弱模型的多样性是毒药。
   默认 temp 0.6~0.7，topk 5~10。
3. **EOS 早停 + 长度封顶 40 token**：防复读（贪心复读已验证会发生）。
4. **上下文 1-shot**（见 L2）：给样例让它"仿写"而不是"填空"。

### L6 设备集成：速度的账要在 C 侧算

- **int4 量化是唯一真提速**（权重字节减半 → 带宽减半 → ~2× tok/s 估算）：
  要做 `export_model.py` 的 int4 路径 + `nnet.c` 的 nibble 解包点积 + 与 int8 的
  逐层误差判据（同源：拿 guide_model.bin 做 A/B，loss 漂移 < 阈值才许换）。
- 两个模型共存：guide 1.18M + chat 1.18M，int8 合计 2.4MB，RAM 无压力，按路由加载。
- 每 token 延迟在模拟器/真机各测一次（本项目铁律：模拟器结论标"未经真机验证"）。

## 五、判据（没有判据的策略是散文）

| 实验 | 判据 | 通过线 |
|---|---|---|
| 训练量档位 | 留出集 loss（chat_eval 2196 对，训练完全没见过） | 相邻档位 val 降幅 <1% 才停 |
| 生成质量 | 100 条人工盲评：通顺/贴题/人设 三选通过率 | ≥60% 才算"能聊" |
| T0 覆盖率 | eval 问句在训练对里的最高相似度分布 | sim≥0.9 占比越高，模型负担越小 |
| T3 1-shot | 同上人工盲评，对比"带样例 vs 不带样例" | 带样例显著优才采用 |
| int4 | 与 int8 的逐层输出差 + 端到端 20 条样本一致性 | 无劣化 + tok/s ×1.8 以上 |

## 五之二、已跑实验的结果（2026-10-16 夜间回填）

### S1 训练量：4k vs 8k（结果见表下说明）
| 档位 | val loss | 状态 |
|---|---|---|
| 4k 步（4000 steps） | 6.0788 | ✅ 完成，`ckpt/model_s4000.npz` |
| 8k 步（全新跑法） | **6.0954** | ✅ 完成，`ckpt/model_s8000.npz` |

**结论：训练量杠杆在 ~4-5k 步就耗尽了。** 8k 的 val（6.0954）与 4k（6.0788）
持平略差，生成样本同为碎片级（均长 3.3→3.7 字，背题率 8/30→3/30，其余无差）。
val 曲线在 step4000 之后就在 6.10~6.17 横盘 —— 这组数据+这个架构的 val 地板
就在 ~6.1。**继续加步数是浪费算力**，S6（12k）已据此取消。
杠杆转向：数据质量/多样性（S5）、训练分布（S2 的 mix，见下）、架构（S7）。

⚠️ 过程记录：8k 跑到 step4200 出现 val 尖峰 6.59（then 回落 6.38→6.26）。
时段上与"S2 实验同机跑"重合——**结论：训练期间别在同机跑重实验**
（loss 值不受 CPU 争抢影响，是训练自身 transient，但时间线和归因都被污染）。

### S2 1-shot prompt（PC 侧，4k 模型，temp0.7/topk10，60 问配对比较）
| 形态 | 均长 | distinct-2 | 与金标 bigram-F1 | 照抄样例 |
|---|---|---|---|---|
| base（无样例） | 2.1 字 | 0.446 | 0.010 | 0/60 |
| sep（`[BOS] 样例问 [SEP] 样例答 [SEP] 新问 [SEP]`） | 1.4 字 | 0.300 | **0.000** | 1/60 |
| eos（样例答用 `[EOS]` 收尾） | 1.8 字 | 0.380 | 0.000 | 0/60 |

**结论（2026-10-16 终判）：mix 实验失败。**
混训模型（8k 步 + 25% 1-shot）val **6.2799**，比两个基线都差（4k 6.0788 / 8k 6.0954）；
输出变长了（base 7.8 字 vs 基线 2.1-3.7 字）但**与金标的 bigram-F1 仍为 0.000**；
且它本命的 1-shot 形态（sep 5.4 / eos 6.9 字）反而比普通形态更短。
即：**训练分布这条杠杆也无效**（与训练量杠杆同样结果）。
→ 模型侧两条路都堵死，剩余变量只剩 **架构容量（S7，进行中）**；
   而真正能出效果的仍是 **S9 检索/分层架构**（S3 已证 15% 精确 + 35% 同话题覆盖）。

### S3 T0 覆盖率（600 条未见问句 vs 21.7 万训练问句，3-gram 包含率）
| 阈值 | 占比 | 架构含义 |
|---|---|---|
| ≥0.95（近乎原句） | **13.4%** | T0 原对答案直接接走，零延迟零胡编 |
| ≥0.80 | 15.7% | 同上（阈值可调） |
| ≥0.60（同话题） | **34.6%** | T2 检索抽取有料可选 |
| ≥0.40 | 61.0% | 弱相关，参考价值有限 |
| 中位数 | 0.50 | — |

### S7 架构容量：2.88M vs 1.18M（同 4000 步、同数据、不混训）
| 架构 | 参数 | val loss |
|---|---|---|
| base（d128/L4） | 1.18M | **6.0788** |
| big（d192/L6） | 2.88M | 6.0966 |

**结论：容量翻倍同样零收益**（token/参数 2.66→1.11，更偏记忆化，val 反而略差）。
至此 **S1 训练量 / S2 训练分布 / S7 容量三条模型侧杠杆全部证伪**，
val 地板 ~6.1 由**数据和任务**决定，不由模型决定。

### S9 检索基线（决定性：检索 vs 生成，500 条未见问句）
| 方式 | 与金标 bigram-F1 | 覆盖 |
|---|---|---|
| 模型生成（4k/8k/mix 三档） | 0.000 ~ 0.010 | 100% |
| 检索：直接返回最佳命中答案 | **0.1352** | 100% |
| 检索 + 置信门控 ≥0.9 | **0.2930** | 15.8% |
| 门控 ≥0.8 | 0.2375 | 29.8% |
| 门控 ≥0.7 | 0.1968 | **51.6%** |

**结论：高置信检索的准确率是模型生成的约 30 倍**，且零延迟、零胡编风险。
**架构决策被数据钉死**：T0(精确命中) → T1(模板) → T2(检索抽取) → T3(模型兜底) → T4(云端)。
模型只在最低置信区间出场 —— 它擅长"没见过也要说点什么"，不擅长"说对"。

**结论（对总纲的量化支撑）**：约 15% 输入可被 T0 零成本接走，约 35% 有同话题
素材可抽取，**真正需要模型硬生成的只剩底部约 1/3**。模型放在长尾的判断被数据证实。

## 七、诚实边界（不变的两条）

1. **这条线的终点是"接得住话的短句闲聊"**，不是深度对话。1.18M~6M 在 3DS 上
   不可能有开放式闲聊；要那个，走云端（T4）。设备端的价值是**离线和零成本**。
2. **每个结论都必须落在产物里可验证**（本项目一贯口径：已完成 = 代码/产物里能验到）。
   本文所有"估算"标注的数字，上机实测后回填本文档，估算变实测。
