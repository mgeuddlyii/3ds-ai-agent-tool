## 二、这一版修掉的四个真缺陷

### 2.1 卡上词表是旧一代（最严重）

`app/data/guide_vocab.txt`（内嵌进 3dsx，10-03 20:19 导出）
与 `ckpt/bpe.pkl`（索引/模型用，10-03 22:51 训练）**脱节**。
4096 个 token id 里 **3815 个对不上**，token 集合**交集 0**。

症状：2 条「检索 0 命中」+ 4 条**命中错误段落**（更隐蔽：有输出、看着像答案），
不报错、不崩、退出码正常。抽取式 X2 趟因此只有 **1/8**。

> ★ 本项目最重要的一条：**`id` 是位置，不是内容。**
> 两份表 V 和 merges 数都相等，只看这两个数字查不出来。

防线：`tools/guia/verify_vocab.py` 逐条比对三方，并已挂进
`tools/build.py` **构建期拦截**（不一致直接拒绝出包）。

### 2.2 单字停用词切碎实体词（本轮新发现）

`entities_of()` 用 `replace` 逐个删停用词，而「之」「有」「中」都在停用表里：

```
「沙之杖有什么效果」
  删 SUBSTR("什么") -> '沙之杖有\x00效果'
  删 EXACT("有")     -> '沙\x00杖\x00\x00效果'← 「之」也命中
  片段               -> ['沙', '杖', '效果']
  实体词             -> ['效果']            ← 「沙之杖」整个消失
```

而 #1085/#1086 段里**确实写着「沙之杖」**——句子是对的，
实体词表里没有它，覆盖判定于是失效。

中招的都是**游戏里最核心的名字**：
`沙之杖` `大师之剑` `时之笛` `心之碎片` `黄金叶` `动力之剑` `风之权杖`

修法：实体词表额外收录**原始问句**的 2~5 字 n-gram 作为兜底；
容量 `ENT_CAP` 8 → 48（原来 8 装不下，后加的兜底词会被前面的挤掉）。

**效果：问句含实体词 13/14 → 14/14 满中。**

### 2.3 `extract.c` 两个死循环洞

在 PC 侧逐行复刻时**真的挂死了**，顺带查出：

| 洞 | 触发条件 | 修法 |
|---|---|---|
| `plen <= 0` 无限循环 | 空段落。`at_end` 既不推进 `i` 也不改 `start` | `if (plen <= 0) continue;` |
| `0xEF` 按 1 字节推进 | 标点后紧跟 `0xEF` 开头字符（它是 3 字节序列首字节）→ 落进续字节 | 改 `i += 3` |

顺带修 `'0'+byte>>4` —— C 里 **`+` 优先级高于 `>>`**，
诊断钩子里的十六进制高位一直算错。

### 2.4 纯标点问法"看起来答对、其实全错"

`？？？` → 全角归一化成 `???` → BPE 切出有意义的 token
→ 命中宝可梦进化石的段落，且 **`matched=True`**。
那个"实体词"根本不是用户想问的东西。

修法：`_degenerate()` 判据 —— 纯标点/空白/单个 ASCII 字母数字 → 回问而非硬答。

⚠️ 第一版把「剔除游戏名后剩余为空」也算退化，
误伤了 `火焰纹章觉醒`（合法问法，答案是游戏概述）。
**「回问」与「回退」是两条不同的路**：本来就没内容才回问，
有内容但被游戏名吃掉了要回退查询。已在函数头写死这条区分。

## 三、`matched` 这个指标不可信（已从界面撤下）

它原本显示成「覆盖 命中 / 未命中」，看起来像准确度。**它不是。**

```
「适合新手吗」     matched=True  实体词「新手」在句里，但答的是御三家
「这游戏卖多少钱」 matched=True  实体词「多少钱」在句里，但答的是带道具
「职业怎么转」     matched=True  但答案里根本没提「转职」
```

`matched=True` 既可能对、也可能错，**与"答对了"没有稳定对应关系**。
界面上已改成只说事实：「含你问的词」/「未含你问的词」。

> 这条本身就是一次判据设计失败：
> **指标必须能区分两条路的输出，且不能与它声称度量的东西脱钩。**

## 四、优化方向（按"实测能不能改善"排序，不按听起来像不像）

### P0 · 同义改写 / 术语切分不一致（唯一的大缺口，0/4 → 目标 3/4）

**问题**：`职业怎么转` 答不出「转职」，`时间怎么重来` 答不出「循环」。

**根因已定位（不是"同义词缺失"，是 BPE 切分不一致）**：

```
问「职业怎么转」
  BPE 编出 -> ['职业', '转']        ← 「转职」被切开了
  语料里写的-> '职业与转职要点'   ← 「转职」是整词
  同一个概念，检索层对不上
```

「职业怎么转」的 token 里**根本没有「转职」**。
所以这不是"缺同义词表"能解决的——**候选段落里有答案（16 个段落写着「转职」），
是查询侧把它切碎了，压根没去查那个词。**

⚠️ 同时实测排除了最容易想到的方案：
**放大检索召回（k 从 4 → 8/12/20）对这 4 条毫无改善（全部 0/4）。**
候选句变多不改变"查询 token 里没有目标词"这个事实。
（k 放大对「实体词在问句」那组也无影响，稳定 14/14 —— 说明它只是个无效旋钮。）

| 方案 | 成本 | 预期 | 判断 |
|---|---|---|---|
| **① 重训 BPE 词表** | 中，要重跑整条链 | **高（直击根因）** | ★ 见 P2，这是同一件事 |
| **② 语料侧建术语同义表**（转职↔职业升级↔转职之证） | 低，但只覆盖已想到的 | 中 | 治标，且难穷举 |
| ③ 用重训后的模型做 query 改写 | 中，要再训练 | 中 | 15.4% 的续写能力可能引入噪声 |
| ~~④ 放大 BM25 召回 k~~ | 一行 | **实测 0 收益** | ❌ 已排除 |

**建议：先做 ①（P2 的 BPE 重训），它同时解决 P0 和"专有名词学不到"两个问题。**
不要先做 ② —— 在切分不一致的前提下，同义表只能一个个手工补，补不完。

### P1 · 语料扩容

755 KB 语料（31 个文件，772683 字节）配 1.2M 参数，`token/参数 = 0.11`，严重欠训练。
**先加语料再谈重训** —— 反过来是浪费算力。

### P2 · BPE 词表重训（升为最高优先级）

**为什么它是 P0 的根因**（见上）：查询侧和语料侧对同一个词的切分不一致，
检索就永远对不上。这不是语料的问题，是**词表的问题**。

现状实测：
- 词表里 3 字以上的 token 占 **20.8%**（427+180+81+45+27+21+…）
- 但**真实专有名词**里能被学成整词的只有 **9.8%**：
  从 31 份语料的章节标题抽出 **265 个 3 字以上专有名词**，
  只有 **26 个**能在词表里找到整词，**239 个（90.2%）被切成 ≥2 块**。
  （本节所有数字均为当日实测，脚本见下）
- 309 个真实专有名词里 **91% 被切成 ≥2 块**
- `配招`→`['配','招']`、`化石`→`['化','石']`、`力量槽`→`2块`、`科学搜查`→`4块`
- 连「转职」这种核心术语都保不住

⚠️ 改 BPE 的**固定动作链**（漏一步就会静默错位，`id` 是位置不是内容）：
```
train_bpe.py → export_vocab.py → build_kb.py → verify_vocab.py → build
```
⚠️ 改 BPE **必须重建 `guide_kb.bin`**（倒排表按 id 存）。
⚠️ 重训后模型也要重训（BPE 变了，token id 空间就变了）。

### P3 · 模型（暂缓）

教师强迫 top-1 从 6.1% 提到 15.4%，但自由生成仍然很差
（单步 15.4% 撑不起 40token 连续生成）。
**当前架构下模型不参与回答**（抽取式只用检索），
所以提升它对 v0.99 的实际表现**没有帮助**。
除非改架构让模型参与，否则不要在这里投入。

### 反向清单：已经证明没用，别再试

- ❌ **让模型给句子打分**（PMI）—— top1 3/8，**比不用模型（6/8）更差**
- ❌ **候选词自动生成** —— 产出「简单说」「通常情况下」这类跨句碎片
- ❌ **算力优化**（wq/wk/wv 合并、8 路展开）—— 实测 +0.003% / 更慢

## 五、0.99 的含义

- **能给用户用**：问句里带上道具名/动作名/游戏名，实测 14/14
- **不完整**：同义改写 0/4；超出 31 款游戏语料范围一律答不了
- **不可信的指标**：`matched` 不代表准确率（见第三节）
- **未经真机验证的部分**：`extract.c` 的三处修改（2.2 / 2.3 / 2.4）
  只有编译通过 + PC 侧复刻器 8/8，**没有模拟器/真机实测**
  （用户 18:52 起要求禁开 Azahar）

**差 0.01 到 1.00 的是什么**（两件事，按顺序）：
1. **BPE 词表重训** —— 这是同义改写 0/4 的**根因**（查询侧把「转职」
   切成 `['转']`，而语料里是整词，检索层对不上）。
   不是"缺同义词表"，所以手工补同义表治标不治本。
2. **真机实测验证** —— `extract.c` 的三处修改至今只有编译 + 复刻器背书。

在这两件事完成前，不打 1.00。

**不打 1.00 的另一个理由**：v0.99 的 14/14 建立在
「答案词是问句里出现的实体词」这个前提上，而**这个前提在真实使用中
未必总成立**。用户更可能问「这个怎么弄」而不是「沙之杖怎么用」。
1.00 意味着这个前提不再重要 —— 那需要先证明它。
