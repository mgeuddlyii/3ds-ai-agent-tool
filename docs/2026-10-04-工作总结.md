## 二、检索修复：1/12 → 12/12

### 起点诊断

先 grep 语料确认：那 11 个"查不到"的答案**全都存在于语料里**
（沙之杖 39 处、心之碎片 77 处、弱点 137 处、转职 40 处）。

→ 所以不是语料不够，是**检索坏**。而检索当时只有 1/12 命中。

### 根因一：索引与语料脱节，12 款游戏从未被索引

`guide_kb.bin` 头里 `n_game=19`，而语料目录有 **31** 个文件。
再往里看 `pass_game` 分布是 `0..18` 各 20~85 段，
外加 `id=23` 和 `id=84` 各 1 段（历史垃圾数据）。

**索引是旧的，后加的 12 款从未进索引。** 重建后 836→1174 段。

### 根因二：两张游戏名表全部错位

`GAME_ORDER`/`GAME_ALIAS`（Python）与 `g_alias`/`g_game_names`（C）
都是**手抄**的 19 款表。逐条对比后发现：

- **全部 19 款的下标都是错的**（`fe_awakening` 真实 id=2，表里写 0）
- 另外 12 款根本不在表里

**后果不是"少支持几款"，而是限定游戏时过滤到别的游戏**——
`gkb_search` 拿 gid 比 `pass_game[pid]`，gid 错位就命中别的游戏的段落，
而现象只是「答案不对」，**不报错也不崩**。

修法：`game_id` 是"按语料文件名字母序的序号"，手抄必然对不上，
所以新增 `tools/guia/gen_game_tables.py` **从语料目录生成**三张表。

### 根因三：MAX_POSTING=24 对 31 款语料太小

实测真实截断规模：**782 个 token 被截断、丢弃 27234 条**。

但目标不是"不丢任何段落"——那要 1153（「的」在 827 段里），
而「的」idf 本来就接近 0，存 827 条既占内存又不带来检索价值。
按真实 df 分层后才知道该管哪一段：

| 真实 df | token 数 | 丢弃 | 该不该管 |
|---|---|---|---|
| 1–5 | 750 | 0 | — |
| 6–15 | 1447 | 0 | — |
| **16–30** | 743 | 659 | **实体词区，截断最亏** |
| **31–60** | 419 | 7648 | **实体词区，截断最亏** |
| 61–120 | 124 | 7328 | 边界 |
| 121+ | 47 | 11599 | 虚词区，**丢了应该丢** |

目标定为「df 16~60 零丢弃」，实测：

| MAX_POSTING | 索引 | 丢 16~60 | C 端倒排 |
|---|---|---|---|
| 24（原） | 563 KB | 8307 | 226 KB |
| **64（新）** | **607 KB** | **0** | **300 KB（可写 784KB 的 38%）** |

只多 44 KB 就让实体词区零丢弃。**两边同改**
（`build_kb.py` 的 `MAX_POSTING` + `guide_kb.h` 的 `GKB_MAX_POSTING`）。

### 让这类脱节不可能再发生：两条编译期断言

历史两次都是"下标表与语料脱节"且**全部不报错**，所以改成让**构建期红**：

```c
/* guide_kb.c：表行数 vs 头文件的编译期常量 */
typedef char game_n_must_equal_GKB_GAME_N[(GAME_N == GKB_GAME_N) ? 1 : -1];
/* sc_guide.c：候选词表行数 vs 游戏数 */
typedef char cand_rows_must_equal_game_count[
    (sizeof(g_cand_set)/sizeof(g_cand_set[0]) == (size_t)GKB_GAME_N) ? 1 : -1];
```

**实测有效**：删掉一行候选词 → `error: size of array ... is negative`。
为此在 `guide_kb.h` 新增 `GKB_GAME_N`（`gkb_game_count()` 是函数，
`sizeof` 里用不了——这是必须新增编译期常量的原因）。

### 最后一个 miss 是评测用例的措辞问题

`boss战第二阶段怎么办`：top1 段原文写的是
「每个 boss 基本都有**两三个形态**，血条打空一次不会结束，通常要**打两轮**」
——讲的**就是**第二阶段机制，只是措辞不同。
原来用「阶段」当判据，等于**要求答案必须用某个词**，那测的是措辞不是内容。

### 一条之前没意识到的约束

按章节标题重选后仍剩 43 处不合格，才发现问题在 BPE：
**它只把高频 2 字词学成整词，3~4 字专有名词全被切开**：

```
科学搜查 → 4 块    女神武器 → 3 块    力量槽 → 2 块
配招     → ['配','招']              化石 → ['化','石']
```

词表 4096 项按汉字数分布：1 字 32.9% / 2 字 35.0% / **3 字以上仅 12.6%**。
而章节标题里 309 个**真实专有名词**，**91% 被切成 ≥2 块**。

### 候选词三道判据（`tools/guia/fix_cand.py` 验，缺一不可）

① `len(bpe.encode(w)) == 1` —— 能整词切分
② 该游戏语料里真的有（判据：`该游戏内含词段 > 0`）
③ 限定该游戏时 top1 正文含该词

第 ② 条抓到最严重的问题：**之前的词是凭空想的**——
`徽章` 在 pokemon_bw 语料里出现 0 次（它在 frlg/sm/xy 里有）、
`变身` 在两款塞尔达里不存在。**数据里没有的东西，换检索算法也没用。**

**31 款 × 6 词现在全部合格。**

## 四、抽取式：让模型「选/拼」而不是「造句」

### 自由生成的实际表现

```
问：火焰纹章觉醒 转职怎么转
答：上的飞行的飞行的飞行。敌人的飞行属性。龙的飞行。前期是是是分十成成成…
```

**教师强迫 top-1 正确率 6.1%（19/312）** —— 连**训练集原文**都续不下去：

| 喂进去的原文 | 模型 top-8 |
|---|---|
| 「…常见的基础职业有剑士、佣兵和战士。」 | `用` `的` `。` `打` `压` `火` `敌人` `水` |

全是虚词，接不上「剑士用剑」。

而且答案 token **就在候选集里**（转职/转职之证/等级十级 全在 134 个
候选 token 中）——所以**不是检索没喂对，是模型给它们的概率不够高**。

### 试过"让模型给句子打分"，结果更差

| 打分方式 | top1 | top3 |
|---|---|---|
| 模型条件对数似然（PMI） | **3/8** | 7/8 |
| 关键词覆盖（**不含模型**） | **6/8** | **8/8** |

**加上模型分数反而变差。** 原因很直白：PMI 高 =「这句接在前文后面很顺」，
而短而通用的句子（「外传关卡的经验值很高」1.398）恰好最顺——
与它 6.1% 的续写能力是同一件事的两面：**它学的是语感，不是内容相关性**。

### 最终方案：按实测把各部分派给擅长的那一层

- **事实层**（这句话说的是不是真的）→ 语料原文，逐字可信
- **筛选层**（哪句在回答这个问题）→ 关键词覆盖，实测 6/8
- **语言层**（怎么把它说得像攻略）→ **暂时空着**（补上只能重训）

PC 侧 `local_chat.py --extract` **8/8 全部给出真答案**：

```
火焰纹章觉醒 转职怎么转 -> 角色等级达到十级以上就能考虑转职。
                             使用转职之证可以把基础职业提升为上级职业。
时之笛 钩索箭哪里拿     -> 钩索箭用来射中远处的目标点发射出去让自己快速移动…
路易吉洋馆2 吸尘器怎么用 -> 金币可以用来提升吸尘器。吸尘器升级后吸力更强。
怪物猎人4G 弱点是什么   -> 影蜘蛛的弱点是水属性。钢龙的弱点是雷属性。
```

⚠️ **但"8/8"要诚实解读**：这 8 条用例的答案词都是**问句里原样出现的词**。
换个不含实体词的问题（"这游戏好玩吗"）覆盖分全是 0，
会退化成"取检索前三句"——那仍然可用，但它不是"答对了"，只是"没答错"。

## 五、C 端移植：1/8，未完成

`shared/nnet/extract.c` + 验收趟 **X2**。**当前 1/8。**

### 途中修掉四个"编译通过、逻辑全错"的坑

1. **切句按字符位置推进，而「。」是 3 字节**（E3 80 82）
   → `start = i + 1` 把 E3 留在上一句尾，下一句从 `80 82` 开始
   → 每句开头都带孤立续字节，而**总字节数只差 1**，肉眼与"字节数"都看不出来
2. **`'。'` 是 multi-character constant**（int 0x3002），与 char 比**恒为假**
   → 切不出任何句子。gcc 报 `-Wmultichar` 但**不是错误**
3. **单字停用词只比首字节**：`query[i]==EX[k][0]` 判「之」（3 字节 E4 B9 8B）
   → 任何以 E4 开头的中文都误命中
4. **判断"要不要补句号"看了错误的变量**：判 `out[w-1]`（上一句尾字节），
   应判**当前句**是否自带句号

### ★★ 顺带发现：中文 UTF-8 在 C 里有四个独立的坑

每个都**只是 warning 或静默**：

| 坑 | 症状 |
|---|---|
| `'。'` 是 multi-character constant | 比较恒为假，逻辑全错 |
| 按字符位置推进多字节字符 | 每句开头带孤立续字节，总长只差 1 |
| 单字停用词只比首字节 | 任何 E4 开头的中文都误命中 |
| 有符号 char 的位运算 | 提升成 int 后高位符号扩展 |

**所以"带 UTF-8 校验的输出断言"不是可选项，是必需品。**
X2 趟一上来就抓到 5 条"输出不是合法 UTF-8"——没有它，这些会全部流到设备上。

### ★★ 顺带发现：停用词表现在有 3 份

`guide_kb.c` 的 `g_stopex`/`g_stopsub`、`extract.c` 的拷贝、PC 的
`STOP_EXACT`/`STOP_SUBSTR`。C 侧原本只有 12 个 vs PC 侧 28 个，
缺的正好是「之/这/那/上/中/会/有/要」这些**高频虚词**。已对齐（EX 29 / SUB 19），
并在 `extract.c` 里写了"改一边必须改另一边"的警告。

### 还没定位的（下次接着查）

C 侧 3 条「检索 0 命中」：gid 正确、rest 正确（`[  转职怎么转]`）、
索引里该词有 16 个 posting、PC 侧同样输入能命中 3 段。
→ 差异必在 `gkb_search` / `gkb_query_tokens` 内部，**还没查**。

另 4 条「答案里没有 X」是覆盖判定失配（候选句里有它但没被选中）。

### 验收工具的一个坑

`azahar_test.py` 的趟次解析是**逐字符**的：

```python
tags = [c for c in args.passes.upper() if c in PASSES]   # ← 只认单字符
```

于是 `--passes X2` 里的 `2` 被丢掉，**静默跑成了 X 趟**——
症状是"我明明要跑 X2，结果打印的是 X 的断言"，而退出码正常、不报错。
已改成按趟次名匹配 + 打印"要跑的趟次"。

### ★★★ 推翻了自己之前的一个错误结论

上一轮我写"训练已到顶、再训也不会更好"。**那是错的。**

`lr_at` 的 cosine 是按 `steps` 参数算退火曲线的，而 `steps` 是
**命令行传的期望值**。上次声明 `steps=4000` 但只跑了 **950 步**，
所以 950 步时 lr 仍是峰值的 **94.6%**——模型**从来没退过火**。

`train.log` 里"留出集 loss 从 step 800 就不再降"那个平台期，
是**高位 lr 下过拟合**，不是收敛。

→ **教训：看到"到顶"先查 lr 走到哪了**，别直接下结论。
已在 `train_gpt.py` 的参数解析处加了注释与提示，把这条钉住。

**看起来像训练挂了，其实训练好好的。** 已改成手动 gbk 解码。

但看 `arch288/` 的时间戳会以为没存。实际在 `ckpt/` 下。

## 九、本轮方法论教训

1. **功能大面积不可用时，先确认数据对不对，再优化计算。**
   静态算力分析再精细，也回答不了"数据是不是最新的"。

2. **看到"训练到顶"先查 lr 走到哪了。** 我据此下的结论方向就错了。

3. **单次数值不足以判趋势。** `eval_holdout.py` 原来有
   `if gap > 0.35: print("真过拟合")`，但实测**留出越多 gap 越小**
   （1 款 +0.68 / 3 款 +0.81 / 5 款 +0.67 / 8 款 +0.26），
   而 3 款只占语料 9.7%——那个量级主要是**小留出集的波动**。
   已改成提示扫 4 个留出规模一起看。

4. **中文 UTF-8 处理在 C 里的坑都只是 warning 或静默**，
   必须靠"带 UTF-8 校验的输出断言"兜住。

5. **"各写各的表"是本项目反复踩的坑**（游戏名表、候选词表、停用词表），
   一律改成脚本生成 + 编译期断言。

6. **测试工具本身也会骗人**：`--passes X2` 静默跑成 X 趟，
   症状是"断言不对"而根因在解析器。
