## 0. 结论先说（TL;DR）

1. **3DS 真有系统级"内置说明书"**：它不是 App 里画一页，而是 title 的
   **第二个 content（index 0001）**，一个叫 **CFA** 的 NCCH 容器
   （NCCH 头 + RomFS，无 ExeFS 代码），由 HOME 菜单选中标题后的
   **「?」按钮**拉起。删掉/改名那个 `.app` 文件，「?」就不加载。
2. **对 AIConsole：只有 `.cia` 形态能带说明书，`.3dsx` 永远不可能。**
   3DSX 不是 title content，系统不认。
3. **PC 侧入口已通**（2026-10-17 临时目录实测）：
   makerom 0.19 支持双 content CIA 打包
   （`-content manual.cfa:1:1`），且接受 IVFC 输入、能产出产品码
   `CTR-P-CTAP` 的正确 CFA。
4. **但内容制作链没通**：`Manual.bcma` 的页面是 **BCLYT 二进制布局**，
   社区没有成熟编辑器，得手写生成器；Azahar **不模拟说明书 applet**
   （二进制里唯一 `bcma` 命中是开机 logo 格式），端到端只能上真机；
   「?」按钮**是否对自制 test-signed title 显示，无公开先例**。
5. **建议分两步**：先做路线 B（App 内说明书屏，风险低、可验收），
   把"说明书该写什么"沉淀成语料；路线 A 作为远期 **go/no-go 实验**——
   一个占位 BCMA 的双 content CIA 上真机，看「?」出不出得来，
   出来再投入 BCLYT 生成器。**排 bug 阶段（现在）什么都不动。**

## 1. 3DS 系统说明书是什么（机制调研）

### 1.1 系统级机制

| 事实 | 说明 |
|---|---|
| 载体 | Title 的 **Content Index 0001**，一个 **CFA（CTR File Archive）** |
| CFA 是什么 | NCCH 头 + RomFS，**没有 ExeFS 代码段**（纯数据容器） |
| 零售产品码 | `CTR-P-CTAP`（NCCH 头 0x150） |
| 入口 | HOME 菜单选中标题 → 按「?」（Manual）按钮 → 系统拉起 manual applet |
| 安装位置 | `sdmc:/Nintendo 3DS/<id0>/<id1>/title/<TID_high>/<TID_low>/content/0001.app` |
| 验证方法 | 删掉/改名 manual `.app` → 点「?」不加载（还原即恢复） |

### 1.2 NCCH 内容类型标记

NCCH 头 flags（+0x188）第 6 字节 `ncchflag[5]`：
**低 2 位 = Form Type，高 6 位 = Content Type**。
Content Type 枚举里 **2 = Instruction Manual**。
（即 flags 字节应为 `0x02 << 2 = 0x08`；makerom 0.19 是否自动置位
**未验证**，可能要后处理补字节——见 §3.3。）

## 2. Manual.bcma 格式（内容制作侧）

`Manual.bcma` = **未压缩的 DARC 归档**，里面是一组 **LZ10 压缩的 DARC
子归档**：

| 子归档 | 内容 |
|---|---|
| `BcmaInfo.arc` | 语言/版本元数据，`./blyt/BcmaInfo.bclyt` |
| `REG_la_index.arc` | 目录页，`Index.bclyt`（PageNum / CategoryNum / SplitNumL / SplitNumS、PageTitle_xxx、Category_xxx） |
| `REG_la_large.arc` / `REG_la_small.arc` | 页面本体：`Page_xxx_size_y.bclyt`（正文）、`Page_xxx_size_bg.bclyt`（背景）、`Page_xxx_size_info.bclyt`（信息栏） |
| `Common_texture.arc` 等 | 公共贴图 |

- 页面是 **BCLYT 二进制布局**（CLYT 格式家族），贴图 **BCLIM**。
- 区域/语言码形如 `EUR_en`、`JPN_ja`。
- **工具现状**：DarcTool（Windows 社区工具）可拆 LZ10 + DARC；
  **BCLYT 没有成熟编辑器**（EFE 只能渲染白页）；
  任天堂 SDK 的 ManualEditor 0.33.0.0 非公开。
- → 结论：BCLYT 页面要么手写二进制布局生成器，要么绕过 BCLYT
  （路线 B 天然绕过，见 §4）。

## 3. 路线 A：HOME 菜单系统说明书

### 3.1 PC 侧打包管线（设计）

```
BCMA 制作（DARC+LZ10，页面=BCLYT 生成器产出）
   └─> Manual.bcma
        └─> mkromfs3ds 打成 RomFS（⚠️ 裸 level-3，makerom 拒收，见 3.2）
             └─> Python 包 IVFC 哈希树外壳
                  └─> makerom -f ncch -o manual.cfa（RSF: CTR-P-CTAP）
                       └─> 与 AIConsole.elf 打双 content CIA：
                           -content AIConsole.cxi:0:0
                           -content manual.cfa:1:1
```

### 3.2 已验证的事实（2026-10-17 临时目录实测，未碰项目文件）

| 项 | 结论 | 证据等级 |
|---|---|---|
| makerom 0.19 支持双 content | ✅ `-exthelp` 确认 `-content <file>:<index>[:<id>]`，官方示例即 `homebrew.cxi:0:0` + `manual.cfa:1:1` | 已核实 |
| makerom 接受 IVFC 输入 | ✅ 喂"IVFC 魔数 + 填充"探针，`-f ncch` 成功产出 12800 字节 CFA，产品码 `CTR-P-CTAP` 落位正确 | 已核实 |
| mkromfs3ds 产物缺陷 | ⚠️ 产出**裸 level-3 RomFS**（无 IVFC 壳），makerom 判 `Invalid RomFS Binary` 拒收——这是项目静态资源当初全走 bin2o 内嵌的同一道坎 | 已核实 |
| IVFC 完整哈希树包装 | ⚠️ 半成品：格式（level 0 头 0x60 + master hash + 各级 SHA-256 树）已查清，Python 包装器**未写完未验证** | 可疑待复核 |

### 3.3 风险与未验证点（按咬人程度排序）

1. **「?」按钮对自制 title 是否显示——无公开先例。**
   社区案例全是给**零售游戏** CIA 注入说明书（如 Asia81 给 Ace Attorney
   注入成功）。自制 test-signed title 带 content 0001 后「?」出不出来，
   没有任何公开记录。**这是路线 A 的 go/no-go 判据。**
2. **说明书 applet 是否接受 `EnableCrypt: false` 的 CFA——未验证。**
   我们的 RSF 一向 `EnableCrypt: false`；零售 CFA 的加密形态不同，
   applet 是否强制校验未知。
3. **Azahar 不能验证。** 二进制里唯一 `bcma` 命中是 `logo.bcma.lz`
   （开机 logo），说明书 applet 未实现 → 端到端**只能上真机**
   （用户有新大三，这条不构成阻塞，但拉长了迭代回路）。
4. **CIA 版本断言偏移会漂移。** 构建期断言（build.py）验 TMD/NCCH 里
   标题版本高字节，偏移是按单 content 布局实测定位的；加第二个 content
   使 TMD 增长，**偏移必然漂移**。届时按项目既有办法重新 diff 定位
   （`-ver 1024` vs `-ver 4096` 两份比字节差），**不准删断言**。
   （2026-10-10 真机报 `0xD8E08027 Invalid or outdated title version`
   就是这条断言在守，别削弱它。）
5. **NCCH flags 的 Content Type=Manual 可能要后处理补字节。**
   makerom 0.19 未见暴露该字段的 RSF 选项；若它不自动置位，
   需要在产出 CFA 后补 `ncchflag[5] = 0x08`——这是对**新产物**的后处理，
   不违反"只能添加"，但要多一道校验步骤。
6. **BCLYT 生成器是从零开始的大件。** 二进制布局格式靠逆向文档，
   一个能产出可渲染页面的生成器工作量最大；且没有本地渲染器可自测
   （EFE 白页），只能真机看效果。
7. **3DSX 形态永远不可能有系统说明书**——只有 `.cia` 可以。
   这意味着路线 A 的成果对 3DSX 用户（开发/调试主力形态）零收益。

## 8. 2026-10-18 实施记录（路线 A 打包链打通）

### 8.1 新增了什么（纯新增，未改既有逻辑）

| 文件 | 作用 |
|---|---|
| `tools/manual/mk_romfs_ivfc.py` | 裸 level-3 RomFS → **套 IVFC 哈希树**（本项目此前没有这个能力） |
| `tools/manual/build_manual.py` | 目录 → IVFC → `app/manual.cfa`，并逐字段校验 |
| `app/manual/root/Manual.bcma` | **占位文件**（真内容未做，见 §8.4） |
| `app/manual.rsf` | 自动生成；`ContentType: Manual`，`UniqueId` 从 `AIConsole_cia.rsf` **同源读取** |
| `tools/build.py` | `cia` 目标改为**两步法**（ELF→CXI→CIA），带说明书 |

### 8.2 关键技术结论（都是本轮实测，不是推测）

1. **`mkromfs3ds` 只产裸 level-3**，`makerom -romfs` 报 `Invalid RomFS Binary`
   —— 与 §3.2 结论一致，**已再次复核确认**。
2. **自己套 IVFC 可行**。物理布局（NO$FUN / 3dbrew 口径）：
   `头(0x60) → master hash(补到 0x1000) → L3 → L1 → L2`，
   每段都补到**绝对 0x1000 边界**（不是"再接一整块"，这一步最容易写错：
   写错会让 L3 落在 0x1060 而不是 0x1000）。
3. 每个哈希覆盖**完整 0x1000 块（含补零）**。产出总长正好 `0x4000`，
   与 3dbrew「总大小至少 0x4000」对上。
4. **`ContentType: Manual` 写进 RSF 就够了** —— makerom 0.19 会自动把
   NCCH flags 置成 `ncchflag[5]=0x09`（高 6 位 = 2 = Instruction Manual）。
   §3.3-5 担心的"要后处理补字节"**不需要做**。
5. **产品码 `CTR-P-CTAP` 正确落位**（NCCH 头 0x150）。
6. **版本断言偏移没有漂移** —— 加了第二个 content 之后，
   `0x2C26`（ticket/TMD 区）与 `0x2F9C`（TMD 内的标题版本）**仍然是 0x10**。
   原因是 TMD 起点由 cert+ticket 长度决定，与 content 数无关；TMD 变长只影响
   **其后的** content 区。→ §3.3-4 的"偏移必然漂移"**实测不成立**，
   断言原样保留、未删未改。

### 8.3 产物与校验（2026-10-18）

- `app/manual.cfa` = 28672 B；`NCCH` magic ✓、`CTR-P-CTAP` ✓、
  `ncchflag[5]=0x09 → ContentType=2` ✓、IVFC 在 0x3000 ✓
- `app/AIConsole.cia` = 3994112 B（单 content 时 3965376 B）：
  - TMD **content 数 = 2**、版本 **v4096**
  - `content[0]` 与 `AIConsole.cxi` **逐字节相同**
  - `content[1]` 与 `manual.cfa` **逐字节相同**
- 另有派生结论：**两步法（ELF→CXI→CIA）与一步 `-elf` 产出不等长**
  （差 2560 B，对齐差异），但版本断言偏移一致。改用两步法是**加入第二个
  content 的唯一途径**（makerom 的 `-elf` 只能产单 content）。

### 8.4 ⚠️ 现在这一步在等什么

**`Manual.bcma` 还是占位文件**（一坨 ASCII 文本，不是 BCMA 归档）。
它的唯一用途是回答 §3.3-1 那个 go/no-go 问题。

**真机测试步骤（用户操作）：**
1. 把 `sd/AIConsole.cia` 拷到 3DS 的 SD 卡任意位置；
2. 用 FBI 安装它（**覆盖安装同一个 title id `00040000-0A1C0100`**）；
3. 回到 HOME，光标停在「测试 0.99」上，**看下屏左下角有没有「?」按钮**；
4. 有 → 按「?」，预期**报错/白屏**（占位内容，属正常），但**只要点了有反应
   （applet 被拉起）就算 go**；
5. 没有「?」→ **no-go**：自制 test-signed title 不被当成"有说明书的标题"，
   路线 A 到此为止，转做路线 B。

**判据只有一条：HOME 上出不出现「?」。** 出现 = 值得投入写 BCLYT 生成器；
不出现 = 后面所有 BCLYT 工作都是白做。

### 8.5 若 go，下一步（BCLYT 生成器）

`Manual.bcma` = 未压缩 DARC，内含一组 LZ10 压缩的 DARC 子归档，
页面是 BCLYT 二进制布局（§2）。要写：
1. DARC 打包器（目录树 → 归档）
2. LZ10 压缩（可先不压，格式允许未压缩？需验证）
3. BCLYT 页面生成器（文本 + 贴图引用）—— **工作量最大**
4. 内容来自 `docs/说明书内容草稿.md`

**本地无法验证渲染效果**（Azahar 不模拟说明书 applet，EFE 只出白页），
只能"改一次 → 上真机看一次"，迭代很慢。所以必须先用 §8.4 的探针确认
值得投入。
