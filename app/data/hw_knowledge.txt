3ds的cpu是几核	两核。core0 是应用（任何程序都能建线程），core1 是系统（要用 APT_SetAppCpuTimeLimit 申请配额），New 3DS 还有 core2（Luma 写死开放，自制程序能用）。我们实测过 core0/core1/core2 都能建线程成功。

3ds能超频吗	能，New 3DS 上最高 804MHz（老 3DS 固定 268MHz）。但走的是 ptm:sysm 服务而不是 APT —— 用 osSetSpeedupEnable(true) 触发内部调 PTMSYSM_ConfigureNew3DSCPU(3)。注意这个函数返回 void，所以「返回 0」不等于成功，得靠事后测频率确认。

3ds的gpu能用来算东西吗	不能。PICA200 在 3DS 上没有向自制程序开放通用计算接口。我们这套推理 100% 跑在 CPU 上。

3ds的dsp能用吗	不能用。DSP 没有开放给 homebrew。

3ds的内存够不够跑模型	够。可写内存约 784KB / 32MB = 2.39%。我们这个 1.2M 参数的 int8 模型连权重带缓存（KV cache 约 132KB）总共不到 2MB，在 3DS 上属于宽裕。

3ds为什么做量化	因为 ARM11 没有 SIMD/NEON，浮点矩阵乘是逐条标量指令。int8 点积能用 DSP 扩展的 smlabb，一次指令干一次乘加，比 f32 快得多。代价是精度，所以要做量化误差控制。

3ds有硬件乘加指令吗	有。ARM11 的 DSP 扩展里有 smlabb（单乘加），还有 smulbb（半字乘）。gcc 在 -O2 下会自己用上，不用手写汇编。但 int8 只能逐字节 ldrsb 取出来喂给它 —— 没有向量加载，这是瓶颈所在。

3ds支持simd吗	不支持。ARM11（ARMv6K）没有 NEON，这是硬件缺失，不是没优化。

3ds支持双精度吗	不支持。ARM11 的 VFP 只有 f32，没有 f64 硬件。写 double 照样生成 vadd.f64，落到 __aeabi_d* 软浮点库上，慢一个数量级以上。判据：反汇编后 grep __aeabi_d 应该是 0 条。

3ds有硬件超越函数吗	没有。exp / log / sin 全是软件例程。我们自己写了 expf / tanhf / rsqrtf / lnf 的定点版。反过来 1.0f/x（vdiv）可以保留硬件版本 —— 一次除法 14 拍，比牛顿迭代划算。

3ds的时钟单位是什么	system tick 是 268MHz —— 不是 60Hz。这是最容易错的地方。除 svcGetSystemTick 返回 tick 之外，其余服务（svcSleepThread / threadJoin / svcWaitSynchronization）的时间参数一律是**纳秒**。把 268MHz 当成 60Hz 用，2 秒超时会变成 34 分钟，而且编译器不报错、程序不崩。

线程放弃能带超时吗	不能。这版 libctru 的 threadJoin 有实现缺陷，timeout 根本没传下去（反汇编可见它只重载 r0 当句柄，从没写 r1:r2）；svcWaitSynchronization 的 timeout 对活线程也不返回。唯一可靠的做法是 svcGetSystemTick 加 svcSleepThread 纳秒，自己轮询一个 volatile 标志。

为什么放弃线程后要把句柄置空	因为不置空的话，一次卡死就会导致之后每次推理都白等 3 秒然后失败 —— 永久降级，而且极难归因（症状出现在「后来所有推理」，不在「当时那次」）。

3ds上什么时候要注意溢出	定长缓冲区。实测踩过两次：一次是调试文本缓冲 2048 字节不够，一次是布局结构的字段判断。另外缓冲区满的现象和程序崩溃的现象在文本证据里一模一样（后面的行凭空消失），所以用「某行不存在」当崩溃判据时必须同时提供一个「证据是否完整」的字段。

写文件会被读到一半吗	会。fopen("w") 一调用就截断，光在读侧加「连读两次一致」治不了根。正确做法是先写 .tmp 再 rename（同一目录内是原子的），读者只会看到完整旧文件或完整新文件，看不到 0 字节。

3ds的缓存有多大	L1 数据缓存 32KB，L2 512KB。这个数字直接决定推理的优化方向：主干权重约 640KB 已经装不进 L2，所以每个 token 都要从主存重读一遍 —— 访存比乘加更值得优化。

3ds的sd卡在哪个位置	/devkitPro 环境下 sdmc 映射成 D:\ 盘，核心目录 D:\_nds\。在程序里路径写作 sdmc:/3ds/aiconsole/ 这样的形式。

3ds怎么读自己的文件	用标准 C 的 stdio（fopen/fread/fwrite）直接读 sdmc:/ 路径。不需要额外的文件系统库，libctru 已经把 newlib 配好了。

3ds怎么测自己的性能	用 svcGetSystemTick 取前后差值。它是 268MHz 的硬件计数器，比任何软件计时器都准。注意配套的等待必须用 svcSleepThread 纳秒，不能用 tick 当毫秒。

怎么知道3ds有没有升频成功	查 PFM 寄存器（0x1FF48014）读的 CPU 频率值；也可以实测 —— 跑一段固定次数的循环，比较升频前后的 tick 数。注意 osSetSpeedupEnable 本身不给返回值。

怎么在3ds上多核跑	threadCreate 的最后一个参数填 core_id。core1 需要先调 APT_SetAppCpuTimeLimit（尽管 Luma 默认给了 89% 的配额，不调也不生效）。插件形态（3dsx / 3gx）同样能用这套 —— 需要的都是运行时授权，不依赖自己的 exheader。

cia能不能设置启动频率	可以，RSF 里写 CpuSpeed: 804mhz，但那只对 .cia 有效，插件形态（3dsx）无效。RSF 里还必须把 ptm:sysm 加进服务列表，否则系统拒绝。

做3ds插件要注意什么	最大的风险是内存不够。申请一大块栈来模拟「内存不足」，threadCreate 会返回 NULL 而不是 abort —— 这反而方便我们测试失败路径。前提是不能 free 一个还在跑的线程（那是 UAF），宁可泄漏。

3ds的ram和rom各多少	3DS 是 128MB（New 3DS 256MB）。绝大多数给 homebrew 用，其余是操作系统和服务的。早期传言里的「64MB」是 New 3DS 之前的数。

3ds怎么申请一块内存	malloc 就够了，我们整个 app（含 1.2M 参数模型、132KB KV cache、408KB 攻略库）常驻不到 3MB。而 3DS 默认可写内存实测约 784KB 是在**单次分配上限**意义上的限制，不是总量限制 —— 所以宁可分多次小分配，也不要一次要一大块。

3ds上怎么计时	用 svcGetSystemTick 取前后差值。它是 268MHz 硬件计数器，比软件计时器准得多。但配套的等待必须用 svcSleepThread 传**纳秒**，不能把 tick 当毫秒用 —— 那一错就是超时时间差 4400 倍。

怎么知道3ds的内存还够不够	两件事分开看：① 常驻内存（看 app 自己的 malloc 总量，相对 128MB 基本不是问题）；② **单次分配上限**（这才是真会撞的墙）。libctru 的内存不足表现为 threadCreate 返回 NULL 或 malloc 返回 NULL，不会 abort —— 所以可以用「故意申请一大块」来测失败路径。

3ds的双核要小心什么	core0 是应用自己的，core1 要先调 APT_SetAppCpuTimeLimit 才真正有配额（尽管 Luma 默认给了 89%）。另外**放弃一个卡住的线程时要连句柄一起置空**，否则一次卡死会让之后每次操作都白等超时再失败 —— 症状出现在「后来所有操作」而不是「当时那次」，极难归因。

3ds上开线程要多大栈	看你要放什么。app 整体搬进工作线程时给了 256KB，因为里面要放 BPE 词表工作区（224KB）。而 3dsx 加载器给主线程的栈**硬编码 16KB** 并忽略你写的 __stacksize__ —— 这条曾让我们崩过一次，是 2026-10-01 的事故根因。

3ds能不能多进程	不能，没有进程概念，只有线程。所谓的「多任务」都是同一个地址空间里的线程切换。

3ds的系统时间怎么取	用标准 C 的 time() 就行（libctru 配好了 newlib）。但注意它返回的是**秒**；要做计时请用 svcGetSystemTick。

cia和3dsx有什么区别	cia 是装进主菜单的正式软件，权限（RSF 里的服务列表、core2、升频）由自己声明；3dsx 是插件形态，跑在别人的进程里。这两者对我们**都成立**的一点是：需要的能力都靠**运行时授权**（ptm:sysm / APT），不依赖我们自己的 exheader。所以升频和双核在两种形态下都能用。
